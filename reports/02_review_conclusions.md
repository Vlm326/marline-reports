# Выводы из обзора


## 1. Что дал обзор

В рассмотренных работах для поиска похожих данных используются компактные представления — сигнатуры или скетчи. Работа Ароновича и соавторов [1] показывает, как такой поиск применяется в дедупликации. Finesse [2] и ODESS [3] посвящены получению признаков, по которым можно находить подходящие чанки для дельта-сжатия.

Для моей задачи из этого следует, что индекс должен работать с уже подготовленными скетчами. Это позволяет сосредоточиться на хранении признаков и поиске кандидатов, а способ вычисления скетча оставить другим модулям Marline. Найденный по скетчу чанк ещё нужно проверить на следующем этапе: высокая оценка сходства сама по себе не гарантирует, что его использование даст хороший результат сжатия.

## 2. Почему выбран обратный индекс

Самый простой способ найти похожий скетч — сравнить запрос со всеми сохранёнными записями. Такой поиск удобно использовать для проверки, но при росте числа чанков он требует всё больше сравнений.

Обратный индекс позволяет сначала отобрать записи с общими признаками. Для каждого признака хранится обратный список — множество ключей чанков, в которых он встречается. При поиске достаточно обратиться к спискам признаков запроса и собрать из них кандидатов.

| Подход | Как выполняется поиск | Что нужно учитывать |
|---|---|---|
| Полный перебор | Запрос сравнивается со всеми скетчами | Прост в реализации, но число сравнений растёт вместе с индексом |
| Обратный индекс | Рассматриваются записи с общими признаками | Нужна дополнительная память для списков; частые признаки могут давать много кандидатов |
| Обратный индекс с эвристиками | Дополнительно ограничивается набор признаков или кандидатов | Возможно ускорение, но есть риск пропустить подходящий чанк |

Для оценки сходства выбран коэффициент Жаккара. Если признаки в скетчах уникальны, положительное значение коэффициента означает, что у скетчей есть хотя бы один общий признак. Поэтому обход всех обратных списков запроса позволяет найти всех кандидатов с положительным сходством.

Ожидается, что такой отбор уменьшит объём поиска по сравнению с полным перебором. Однако это зависит от данных: если одни и те же признаки встречаются почти во всех чанках, списки будут длинными и выигрыш может оказаться небольшим. Проверить это предстоит экспериментально.

## 3. Какую архитектуру я выбрал

По итогам обзора спроектированы архитектура и программный интерфейс `marline_index`. Выделены три части: интерфейс скетча, интерфейс индекса и интерфейс хранилища. Такое разделение позволяет менять способ хранения данных, сохраняя общий порядок работы с индексом.

Интерфейс индекса предусматривает добавление и удаление записей, поиск наиболее похожих чанков и очистку. Типы ключей и признаков предполагается задавать параметрами, чтобы модуль можно было использовать с разными представлениями чанков.

Первое хранилище планируется сделать в оперативной памяти на основе `HashMap` и `HashSet`. Это позволит проверить основные операции без подключения базы данных.

Обратный индекс сам по себе является известной структурой. Содержание моей работы — разработать подходящий для Marline модуль и исследовать, насколько хорошо он сокращает поиск по скетчам, используемым в проекте.

## 4. Что нужно учесть при реализации

Перед реализацией важно определить поведение операций. В частности, нужно решить, что происходит при повторной вставке одного ключа, как обновляется скетч и как удаляются связанные с ним записи из обратных списков. Эти правила нужны, чтобы данные в индексе оставались согласованными.

Также необходимо определить, допускаются ли повторяющиеся признаки и скетчи разной длины. Формула Жаккара для множеств предполагает уникальность элементов; если хранить повторы, подсчёт совпадений нужно согласовать с выбранным представлением.



## 5. Дальнейшая работа

На текущем этапе результатом первой задачи стали архитектура модуля и определение его интерфейсов. Далее планируется:

1. Реализовать хранение скетчей и обратных списков, добавление, удаление и обновление записей.
2. Реализовать поиск кандидатов и их ранжирование по коэффициенту Жаккара.
3. Подготовить тесты основных операций и линейный поиск для проверки результатов.
4. Исследовать влияние частоты признаков и эвристик на число кандидатов, время поиска и полноту выдачи.
5. Провести измерения на синтетических и реальных данных, учитывая затраты памяти.

Цель и основные задачи из [постановки](goal.md) сохраняются. Обзор помог выбрать устройство индекса и определить вопросы, которые нужно проверить при реализации. Утверждать, насколько он ускорит поиск и какие параметры окажутся лучшими, можно будет после экспериментов.
