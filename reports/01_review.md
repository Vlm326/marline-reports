# Обзор литературы, подходов и инструментов



## 1. Предмет и границы обзора

Цель работы — разработать и исследовать обратный индекс, сокращающий число рассматриваемых чанков при поиске базы для дельта-сжатия в Marline. 

Предмет обзора — организация обратного индекса: хранение связей между признаками и ключами чанков, формирование кандидатов, ранжирование по сходству и сокращение объёма поиска. Индекс получает готовые sketch от других модулей Marline. Разработка алгоритмов разбиения данных, извлечения признаков и дельта-кодирования в мой вклад не входит; связанные публикации рассматриваются только с точки зрения требований к индексу.

При дедупликации одинаковые чанки можно обнаруживать по хешам содержимого. Для похожих, но различающихся чанков требуется другой механизм: найти подходящий базовый чанк и сохранить различия. Sketch служит компактным представлением для предварительного поиска. Его сходство не доказывает равенство исходных данных и не гарантирует минимальный размер дельта-кода.

## 2. Поиск похожих данных по сигнатурам

Аранович и соавторы описывают систему дедупликации, использующую компактные сигнатуры для обнаружения похожих данных (похожие на как раз скетчи, которые используются в нашей системе) . Найденное сходство используется для последующей обработки содержимого; авторы также обсуждают сочетание поиска по сходству с проверками идентичности. [источник 1](https://u.cs.biu.ac.il/~tomi/Postscripts/systor.pdf).

Для Marline это означает, что индекс должен возвращать кандидатов, а решение об использовании базы должно приниматься на следующем этапе. Ложноположительный результат по скетчу не должен приводить к некорректному восстановлению данных. Кроме того, критерий качества индекса должен учитывать не только совпадение sketch, но и фактическую полезность найденного чанка для сжатия.

## 3. Finesse: локальные признаки и super-features

Finesse посвящён обнаружению похожих чанков для дельта-сжатия после дедупликации. Авторы выделяют стоимость многократных преобразований отпечатков в N-transform SF и используют локальность признаков: чанк разбивается на части, признаки вычисляются по частям и объединяются в супер фичи. [Публикация USENIX, источник](https://www.usenix.org/conference/fast19/presentation/zhang).

Работа показывает, что стоимость построения представления сама может быть существенным этапом поиска. Для индекса это аргумент в пользу интерфейса, принимающего уже вычисленные признаки. Тогда разные способы построения sketch можно сравнивать при неизменной структуре хранения. При этом супер фичи являются частью схемы представления: нельзя считать, что коэффициент Жаккара любых наборов таких значений автоматически имеет одинаковую связь с похожестью исходных чанков.

## 4. ODESS: сокращение стоимости извлечения признаков

ODESS использует content-defined sampling для формирования меньшего набора хешей, к которому применяются преобразования, а также быстрое Gear-хеширование. Основной предмет работы — снижение затрат обнаружения похожести при сохранении качества отбора для устранения избыточности. [Аннотация IEEE и сведения о публикации, источник ](https://ieeexplore.ieee.org/document/9458911/).

Часть подхода ODESS используется в нынешнем проекте: в проекте имеется `OdessHasher`, а командный бенчмарк преобразует результат его работы в скетчи.##
## 5. Обратный индекс и коэффициент Жаккара

В рассматриваемой архитектуре обратный список сопоставляет признаку множество ключей чанков. Запрос обращается к спискам своих признаков, объединяет ключи и подсчитывает совпадения. Для множеств признаков `A` и `B` коэффициент Жаккара равен:

`J(A, B) = |A ∩ B| / (|A| + |B| − |A ∩ B|)`.

Если оба скетча содержат по `s` уникальных признаков, достаточно знать число общих признаков `o`: `J = o / (2s − o)`. Такую схему реализует обычный `InvertedSketchIndex`. Называть эту оценку точной можно при выполнении предпосылок о длинах и уникальности. При произвольных длинах нужно знать обе длины; при дубликатах необходимо определить другую семантику либо удалить повторы.

Пример: для `[1, 2, 3]` и `[1, 2, 4]` пересечение содержит два элемента, объединение — четыре, поэтому `J = 0.5`. Скетч без общих признаков можно исключить, если нужны только положительные оценки. Пропуск же списка частого признака способен изменить как состав кандидатов, так и подсчитанное сходство.

Это аналитическое обоснование структуры, полученное из определения метрики и устройства кода; оно не приписывается перечисленным статьям как предложенный в них алгоритм данного модуля.

## 6. Архитектура индекса и выбранные инструменты

На первом этапе спроектированы архитектура и программный интерфейс модуля `marline_index`. Определены основные сущности: идентификатор чанка, его sketch и обратный список, связывающий признак с идентификаторами чанков. Индекс принимает уже подготовленные sketch; способ получения признаков остаётся за пределами модуля.

Архитектура разделена на три части:

| Компонент | Ответственность |
|---|---|
| Интерфейс sketch | Предоставление признаков и размера представления чанка |
| Интерфейс индекса | Добавление и удаление записей, поиск наиболее похожих чанков и очистка индекса |
| Интерфейс хранилища | Доступ к связям между ключами, sketch и обратными списками |

Такое разделение позволяет разрабатывать поиск независимо от конкретного способа хранения данных. Типы ключей и признаков предполагается задавать параметрами, чтобы интерфейс можно было использовать с разными представлениями чанков.

Для реализации выбран Rust, на котором написан Marline. Cargo будет использоваться для сборки модуля и запуска тестов, Rustdoc — для описания интерфейсов и требований к их использованию. Для первой реализации хранилища планируется использовать стандартные коллекции `HashMap` и `HashSet`: они позволяют представить соответствия между признаками и множествами ключей без подключения отдельной базы данных.

Результат первой задачи — архитектурное разделение модуля и определение операций его интерфейса. Следующие этапы включают реализацию хранения sketch и обратных списков, согласованного изменения записей и поиска по коэффициенту Жаккара. После получения базовой реализации планируется подготовить линейный поиск для сравнения, исследовать эвристики отбора кандидатов и провести измерения времени, памяти и качества поиска.
